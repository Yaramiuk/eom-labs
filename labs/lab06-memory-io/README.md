# Lab 6. Віртуальна пам'ять, File Descriptors та I/O

Робив у Docker на Linux ARM64 (ядро 7.0.12-linuxkit, gcc 13.5, strace 6.1), бо strace під емуляцією x86-64 в мене не працює. getconf PAGE_SIZE показав 4096. Другий термінал замінив фоновими процесами. Варіанти з lseek і fflush зробив через -DUSE_LSEEK і -DUSE_FFLUSH, щоб залишились обидві версії.

# Частина 1. Віртуальна пам'ять

## Завдання 1. Де лежать дані

| Об'єкт | Run 1 | Run 2 | Run 3 |
|---|---|---|---|
| function | 0x400744 | 0x400744 | 0x400744 |
| initialized global | 0x420048 | 0x420048 | 0x420048 |
| uninitialized global | 0x420054 | 0x420054 | 0x420054 |
| static | 0x42004c | 0x42004c | 0x42004c |
| heap | 0x1df462a0 | 0x2630e2a0 | 0x38cb12a0 |
| local | 0xfffffbd78f44 | 0xffffdca526c4 | 0xffffc17710f4 |

- Близько лежать глобальні і статичні змінні.
- Heap не схожий на адреси глобальних, він окремо.
- Stack в зовсім іншій області, на самому верху.
- Код і глобальні однакові в кожному запуску (файл не PIE), а heap і stack змінюються. Це ASLR.

Всі ці адреси віртуальні, а не фізичні адреси в RAM.

## Завдання 2. Memory map

memory_maps вивела PID 95, main 0x400884, global 0x420060, heap 0x269ec2a0, stack 0xffffde5b1fa4. Порівняв з /proc/95/maps:

| Що | Адреса | Рядок у maps | Права |
|---|---|---|---|
| main | 0x400884 | 00400000-00401000 memory_maps | r-xp |
| global | 0x420060 | 00420000-00421000 memory_maps | rw-p |
| heap | 0x269ec2a0 | 269ec000-26a0d000 [heap] | rw-p |
| stack | 0xffffde5b1fa4 | ffffde592000-ffffde5b3000 [stack] | rw-p |

Heap всередині [heap] і stack всередині [stack], все сходиться. Ще там видно libc.so.6, ld-linux і libstdbuf.so. Останній з'явився, бо я запускав через stdbuf.

r це читання, w запис, x виконання, p private. Код не треба робити writable, щоб його не можна було випадково або навмисно переписати. Дані не треба робити executable, щоб не можна було виконати код, який хтось записав у буфер. Ці права перевіряє процесор (MMU) при кожному зверненні, це і є memory protection.

## Завдання 4. Heap і віртуальна пам'ять

malloc на 100 МБ дав адресу 0xffff97b8f010.

| Момент | VmSize | VmRSS |
|---|---|---|
| після malloc | 104748 kB | 1296 kB |
| після запису в кожну сторінку | 104748 kB | 103692 kB |

VmSize одразу 100 МБ, а реально зайнята пам'ять (VmRSS) спочатку майже нуль. Тільки коли я записав по байту в кожну сторінку, RSS виріс на 100 МБ. Тобто malloc спочатку тільки резервує адреси, а фізична пам'ять дається при першому зверненні до сторінки.

Ще помітив, що такий великий malloc лежить не в [heap], а в окремому анонімному mmap.

## Завдання 5-6. Invalid memory access

invalid_memory надрукувала About to access invalid memory і впала з Segmentation fault, exit status 139 (128 + 11, тобто SIGSEGV). Друге повідомлення не надрукувалось.

strace в кінці показав:

```
--- SIGSEGV {si_signo=SIGSEGV, si_code=SEGV_MAPERR, si_addr=NULL} ---
+++ killed by SIGSEGV +++
```

SEGV_MAPERR означає, що за цією адресою нічого не відображено, а si_addr=NULL, що це адреса 0.

- За адресою 0 писати не можна, бо ця сторінка спеціально не відображена, щоб помилки з NULL одразу ловились.
- Процес не може залізти в чужу пам'ять, MMU зупиняє доступ і ядро вбиває тільки цей процес.
- Segmentation fault не означає, що RAM зламана, це помилка в програмі.

# Частина 2. File descriptors

standard_fds вивела 0, 1, 2.

|---|---|---|
| 0 | /dev/null | /dev/null |

stdin у мене /dev/null, бо контейнер без вводу. stdout залежить від того, куди я перенаправив вивід. Тобто 0, 1, 2 не обов'язково термінал, це може бути файл або pipe.

## Завдання 8. Відкриття файлу

open_file вивела Opened file descriptor: 3, і в /proc/PID/fd з'явився 3 -> example.txt.

Вийшло 3, бо 0, 1, 2 вже зайняті, а ядро дає найменший вільний номер. Але завжди розраховувати на 3 не можна.

"example.txt" це ім'я файлу, а 3 це номер, який ядро видало після open. Далі read і write працюють тільки з номером, ім'я їм вже не потрібне.

## Завдання 9. write

write_file вивела Requested: 19 bytes і Written: 19 bytes, у output.txt Hello from write().

- message лежить у стеку main, тобто у віртуальній пам'яті процесу.
- fd це дескриптор відкритого output.txt.
- size це скільки байтів записати, тут 19.
- write повертає, скільки байтів реально записалось, або -1.

write може записати менше, ніж просили, тому в нормальній програмі треба дописувати решту в циклі. Це я зробив у file_copy.

## Завдання 10. read

read_file вивела обидва рядки з input.txt. read повертає кількість прочитаних байтів, 0 коли кінець файлу і -1 при помилці. Файл 35 байтів, буфер 16, тому читання йшло 16, 16, 3 і потім 0.

## Завдання 11-12. Offset і lseek

Прогноз: другий read не прочитає ті самі байти, бо позиція зсунеться.

| Версія | First | Second |
|---|---|---|
| без lseek | Compu | ter S |
| з lseek(fd, 0, SEEK_SET) | Compu | Compu |

Після першого read offset став 5, тому другий почав звідти. lseek повернув offset на початок.

Sequential access це коли читаєш підряд і offset сам зсувається. Random access це коли сам ставиш позицію через lseek і читаєш з будь-якого місця.

## Завдання 13. strace для read_file

```
openat(AT_FDCWD, "input.txt", O_RDONLY) = 3
read(3, "Computer Systems", 16)         = 16
write(1, "Computer Systems", 16)        = 16
read(3, "\nOperating Syste", 16)        = 16
write(1, "\nOperating Syste", 16)       = 16
read(3, "ms\n", 16)                     = 3
write(1, "ms\n", 3)                     = 3
read(3, "", 16)                         = 0
close(3)                                = 0
```

Тут весь цикл: open, read, write, read = 0 (кінець файлу) і close. open у C в ядрі називається openat. Перед цим дескриптор 3 займав завантажувач для libc, потім закрив, тому input.txt знову отримав 3.

## Завдання 14. stdout і stderr

| Команда | На екрані | У файлі |
|---|---|---|
| ./streams | обидва рядки | - |
| ./streams > normal.txt | Error output | Normal output |
| ./streams 2> errors.txt | Normal output | Error output |

З > у файл пішов тільки stdout, а stderr залишився на екрані. strace показав, що програма в обох випадках робить той самий write(1, ...) і write(2, ...). Змінилось тільки те, куди вказує fd 1, це зробив shell перед запуском. Тому програмі не треба знати, що її вивід у файлі.

## Завдання 15-16. printf, write і fflush

| Версія | Вивід | write у strace |
|---|---|---|
| без fflush | DABC | write(1, "D", 1), потім write(1, "ABC", 3) |
| з fflush | ABCD | write(1, "ABC", 3), потім write(1, "D", 1) |

Три printf дали один write з ABC. Без fflush D вийшла першою, бо printf тримав ABC у буфері до кінця програми, а write пішов одразу. Навіть у терміналі було DABC, бо там немає \n. fflush примусово скидає буфер, і порядок стає таким, як у коді.

# Фінальне завдання file_copy

Копіює через open, read, write і close з буфером 4096. Окрема функція write_all дописує в циклі, якщо write записав не все, і повторює виклик при EINTR. Якщо не вдалося відкрити destination, source закривається. Результат close теж перевіряю.

Перевірка:

| Що копіював | cmp | Примітка |
|---|---|---|
| source.txt (текст) | 0 | однакові |
| сам file_copy (бінарник) | 0 | 70912 байтів обидва |
| 10 МБ з /dev/urandom | 0 | sha256 однаковий |
| порожній файл | 0 | |

Для 10 МБ strace -c показав 2442 write і 2444 read. 10000000 / 4096 це 2442 блоки, плюс один read, який повертає 0, і ще один read робить завантажувач для libc.

У копії права 0644, а не rwx, бо програма копіює тільки вміст, а права не переносить.

Текст і бінарник копіюються однаково, бо read і write працюють просто з байтами і не знають, що в них.

Помилки:

| Випадок | Повідомлення | Exit |
|---|---|---|
| немає аргументів | Usage: ./file_copy <source> <destination> | 1 |
| source не існує | open source 'nosuchfile.txt': No such file or directory | 1 |
| не можна відкрити destination | open destination '/nonexistent_dir/x.txt': No such file or directory | 1 |
| source це папка | read: Is a directory | 1 |
| немає місця (/dev/full) | write: No space left on device | 1 |

У strace для випадку з поганим destination видно, що після помилки є close(3), тобто source закрився.

strace для нормального копіювання:

```
openat(AT_FDCWD, "source.txt", O_RDONLY) = 3
openat(AT_FDCWD, "destination.txt", O_WRONLY|O_CREAT|O_TRUNC, 0644) = 4
read(3, "Operating Systems\nComputer Archi"..., 4096) = 40
write(4, "Operating Systems\nComputer Archi"..., 40) = 40
read(3, "", 4096)                       = 0
close(3)                                = 0
close(4)                                = 0
```

Два openat це два open у коді, далі один read і один write на 40 байтів, read = 0 це кінець і два close.

Шлях даних: файл source, потім ядро через read копіює дані в buffer у пам'яті мого процесу, потім write знову через ядро записує їх у destination.

## Інтеграційне питання

buffer лежить у стеку, тобто це віртуальна адреса в моєму процесі, і займає одну або дві сторінки. fd це номер у таблиці відкритих файлів процесу. read це системний виклик, процесор переходить у режим ядра. Ядро за fd знаходить файл і offset, бере дані і копіює їх за адресою buffer. MMU перекладає цю віртуальну адресу у фізичну. Потім ядро зсуває offset, повертає кількість байтів, і програма продовжує роботу з даними в buffer.

## Контрольні питання

1. Virtual address це адреса, яку бачить програма.
2. Physical address це реальна адреса в RAM. Віртуальну у фізичну перекладає MMU по таблиці сторінок.
3. Virtual address space це всі адреси, які є у процесу (код, дані, heap, stack і т.д.).
4. Два процеси можуть мати однакову віртуальну адресу, бо в кожного своя таблиця сторінок.
5. Page це шматок пам'яті фіксованого розміру, у мене 4096 байтів.
6. Page frame це такий самий шматок, але у фізичній RAM.
7. Page table це таблиця, яка каже, яка віртуальна сторінка в якому фреймі, і які в неї права.
8. MMU перекладає адреси і перевіряє права при кожному зверненні.
9. TLB це кеш для перекладів адрес, щоб кожного разу не лізти в таблицю.
10. TLB miss значить, що перекладу немає в кеші, але сторінка є, і його просто беруть з таблиці. Page fault значить, що сторінки немає або доступ заборонений, і тоді вже розбирається ядро.
11. Page fault це виняток, коли звертаються до сторінки, якої немає в пам'яті або куди не можна.
12. Page fault не завжди помилка. Наприклад, при першому записі в malloc-пам'ять page fault нормальний, так ядро і дає фізичну пам'ять.
13. Процеси ізольовані, бо в кожного своя таблиця сторінок і чужої пам'яті в ній просто немає.
14. r читання, w запис, x виконання.
15. Код не writable, щоб його не можна було переписати.
16. malloc не дорівнює одразу RAM, бо фізична пам'ять дається тільки при першому зверненні до сторінки. В експерименті RSS виріс тільки після запису.
17. File descriptor це номер відкритого ресурсу в процесі.
18. Pathname це ім'я файлу, а fd це номер, який дали після open.
19. 0 stdin, 1 stdout, 2 stderr.
20. open знаходить файл, перевіряє права і повертає fd.
21. read повертає кількість прочитаних байтів.
22. read == 0 означає кінець файлу.
23. write повертає кількість записаних байтів.
24. Partial write треба враховувати, бо write може записати не все, і решта загубиться.
25. File offset це поточна позиція у файлі.
26. lseek змінює позицію у файлі.
27. FILE * це структура з stdio з буфером, а всередині неї є fd.
28. printf не одразу викликає write, бо збирає текст у буфер.
29. Buffering це коли дані тимчасово накопичуються, щоб робити менше системних викликів.
30. fflush скидає буфер, тобто викликає write прямо зараз.
31. > працює без зміни коду, бо shell підміняє, куди вказує fd 1, а програма просто пише в 1.
32. file_copy копіює і текст, і бінарники, бо працює з байтами.
33. Під час read buffer лежить у віртуальній пам'яті процесу, а фізично в RAM, куди MMU відобразив його сторінку.
34. Процес передає ядру fd і адресу буфера, ядро знаходить файл і копіює дані в пам'ять процесу.

## Висновок

Я побачив, що всі адреси в програмі віртуальні, а в /proc/PID/maps видно області коду, даних, heap і stack з різними правами. Сторінка 4096 байтів, і malloc реально займає пам'ять тільки коли в неї пишеш. Запис за NULL закінчився SIGSEGV. У другій частині розібрався, що fd це просто номер, за яким може бути файл, pipe чи термінал. Подивився, як рухається offset, як працює > і чому printf виводить пізніше за write. file_copy копіює будь-які файли байт у байт і нормально обробляє помилки.
